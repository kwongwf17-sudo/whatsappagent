# Current stages and daily history

The dashboard customer list uses the current business date, regardless of the date selected for analytics. The selected date still controls dated reports and the new Stage History panel. A retained customer older than Day 10 appears in DAY 11+, while existing opt-out, order, fresh journey, import clock and stale-deletion rules keep their priorities. The DELETE label filter is removed from the customer and follow-up monitors; the Deleted archive remains available.

Stage History uses the existing JSON document adapter and PostgreSQL `json_documents` table. There are no new tables or infrastructure services. Each account has a current stage index and one document per recorded business date. Reports contain opening/baseline counts, closing counts, and customer movements with IDs, stages, timestamps and reasons. For each stage, opening + entered − exited = closing. The baseline date is explicitly a partial day; dates before tracking began return no history rather than reconstructed totals. Missing observation days are not invented, and the resumed report is marked partial.

The follow-up runner observes calendar progression before cleanup, including when the worker is configured for queue-only operation. Dashboard reads also refresh the observation. Customer creation, stage-changing updates, opt-outs, orders, journey resets, deletion and duplicate merging update history. Ordinary updates that leave the stage unchanged do not append movements or rewrite the history documents. Direct administrative changes outside the customer store are identified as reconciled changes on the next observation.

In PostgreSQL, account advisory locks serialize history updates across web and worker processes. Customer row upserts, individual deletions and duplicate merges write their history in the same transaction. A failed history write rolls back the customer mutation. Historical movement IDs are not rewritten by later duplicate merges. JSON/demo storage uses the existing atomic file writes and an in-process history write queue; it does not provide PostgreSQL's multi-document transaction guarantees.

The deployment does not recalculate queued send dates, merge additional customers, or expand deletion eligibility. Account-data purges also remove that account's history. The first production observation establishes the baseline; older daily counts cannot be recovered as verified snapshots.

Tests cover business-date rollover, daily arithmetic, immutable previous reports, same-day state changes, partial days, repeated observations, account isolation and history gaps. The real dashboard/import HTTP test verifies current labels when an old date is selected, DAY 11+, the removed DELETE filter, saved movements, and inline JavaScript syntax. PostgreSQL integration tests use temporary isolated schemas to verify concurrent adapters, transactional rollback, deletion reasons, duplicate merging and retained historical identities.
